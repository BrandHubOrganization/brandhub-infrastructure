1. Login — Access Token Generation

Giải thích sơ đồ 1 — Login

①
Client gửi yêu cầu đăng nhập

Trình duyệt hoặc mobile app gửi POST /api/v1/auth/login với email và password đến Business Service thông qua API Gateway. Lưu ý: request login là public endpoint, không cần JWT, nên Gateway không kiểm tra token cho route này.

②
AuthService xác thực thông tin

Business Service kiểm tra email có tồn tại trong database không. Nếu có, dùng BCrypt.matches() để so sánh password người dùng nhập với hash đã lưu. Nếu sai → ném exception, trả về 401.

③
JwtUtil tạo Access Token

Sau khi xác thực thành công, JwtUtil xây dựng JWT với:

  • sub = userId (UUID) — định danh duy nhất người dùng
  • role = MemberRole (OWNER, CREATOR, VIEWER, CLIENT, ACCOUNT)
  • workspaceId = workspace hiện tại
  • jti = UUID ngẫu nhiên — mỗi token có jti khác nhau, dùng cho blacklist sau này
  • iat = thời điểm tạo, exp = 15 phút sau

Toàn bộ payload được ký bằng private.pem với thuật toán RS256. Chữ ký này đảm bảo không ai sửa được nội dung token.

④
Trả token về Client

Server gửi response 200 OK với { accessToken, refreshToken } trong body. Access token có thời hạn 15 phút, refresh token 30 ngày. Refresh token được đặt trong cookie httpOnly (không thể đọc bằng JavaScript) để tăng bảo mật.

Điểm quan trọng: Business Service dùng private.pem để ký. Private key này không bao giờ rời khỏi Business Service — không gửi qua mạng, không lưu trong database. Đây là nguyên tắc bảo mật cốt lõi của RS256.

2. Request — Gateway Verifies Token

Giải thích sơ đồ 2 — Request / Gateway Verify

①
Client gửi request với Access Token

Sau khi đăng nhập thành công, client lưu access token. Mỗi request đến API đều kèm header Authorization: Bearer {access_token}. Token do Business Service ký RS256, thời hạn 15 phút.

②
Gateway trích xuất token từ header

JwtAuthFilter lấy HTTP header Authorization. Kiểm tra có bắt đầu bằng "Bearer " không. Nếu không có header hoặc sai format → trả 401 ngay. Nếu hợp lệ, cắt bỏ "Bearer " → lấy JWT string.

③
JwtUtil.validateAndExtract() — verify chữ ký RS256

Đây là bước quan trọng nhất. Gateway dùng public key (public.pem) để xác minh chữ ký của token:

  • Tách JWT: header + payload + signature
  • Băm SHA-256 phần base64(header).base64(payload) → tạo hash mới
  • Giải mã signature bằng public key → lấy hash gốc (do Business Service tạo lúc ký)
  • So sánh: bằng nhau → hợp lệ; khác nhau → token đã bị sửa

Nếu hết hạn (exp < now) → ExpiredJwtException. Nếu chữ ký sai → SignatureException. Filter bắt tất cả lỗi JWT → trả 401.

④
Kiểm tra Redis Blacklist

Lấy jti (JWT ID) từ claims. Gọi Redis EXISTS jwt:blacklist:{jti}. Nếu key tồn tại → token đã bị thu hồi (logout) → trả 401. Nếu không tồn tại → token còn hiệu lực. Token không có jti (từ hệ thống cũ) → bỏ qua blacklist check.

⑤
Inject headers và forward request

Gateway thêm headers vào request:

  • X-User-Id = claims.sub (userId)
  • X-User-Role = claims.role (quyền workspace)
  • X-Workspace-Id = claims.workspaceId

Sau đó forward đến Business Service — service này đọc headers để biết user, không cần xác thực lại JWT. Nếu token không hợp lệ, Gateway không forward đi đâu cả, chỉ trả 401.

Điểm quan trọng: Gateway dùng public.pem — chỉ verify, không thể ký. Hacker lấy được public key từ Gateway vẫn không thể tạo token giả vì thiếu private key ở Business Service. Đây là lợi thế bảo mật cốt lõi của RS256 so với HS256.

3. Logout — Token Blacklist

Giải thích sơ đồ 3 — Logout / Token Blacklist

①
Client gửi yêu cầu logout

Gửi POST /api/v1/auth/logout kèm access token trong header Authorization: Bearer {AT} và refresh token trong cookie refreshToken. Route này được Gateway forward đến Business Service vì cần xử lý logic nghiệp vụ.

②
Business Service verify access token

AuthService gọi jwtUtil.parseToken(AT) — dùng public key (business-service cũng có public.pem) để verify RS256, lấy claims. Mục đích: lấy userId và jti từ token. Nếu token hết hạn hoặc sai chữ ký, logout vẫn được xử lý (token sắp hết hạn vẫn cần blacklist).

③
Blacklist token vào Redis

blacklistToken() lấy jti (JWT ID) từ claims và lưu vào Redis:

SETEX jwt:blacklist:{jti} {TTL} "true"

TTL = token.exp - System.currentTimeMillis(). Nghĩa là key tồn tại đúng bằng thời gian còn lại của token. Khi token hết hạn tự nhiên, Redis tự động xóa key — không cần cron job cleanup. Cả access token và refresh token đều bị blacklist.

④
Ghi Audit Log và xóa cookie

Lưu sự kiện logout vào database: userId, IP address, user-agent, timestamp. Mục đích: kiểm toán bảo mật, phát hiện đăng nhập bất thường. Trả response 200 kèm lệnh clear cookie refreshToken cho client.

⑤
Request sau logout bị từ chối

Khi client gửi request với token đã logout, Gateway kiểm tra Redis: EXISTS jwt:blacklist:{jti} → true → trả 401. Client buộc phải đăng nhập lại để có token mới.

Điểm quan trọng: JWT là stateless — không thể thu hồi sau khi đã ký. Cơ chế blacklist là bắt buộc. Client-side deletion không đáng tin (attacker có thể copy token trước khi logout). Server-side blacklist với TTL tự động cleanup là giải pháp đúng cho JWT. Vì access token chỉ sống 15 phút, blacklist TTL ngắn → Redis không bị đầy.

Giải thích sơ đồ 4 — Kiến trúc tổng thể

①
Client / Browser

Điểm xuất phát. Người dùng tương tác qua giao diện web dashboard (port 3000) hoặc mobile app. Client lưu access token và gửi kèm mỗi request qua header Authorization: Bearer {token}. Refresh token lưu trong cookie httpOnly không thể đọc bằng JavaScript.

②
API Gateway — tuyến đầu bảo mật

Gateway là cổng vào duy nhất cho tất cả request. Chịu trách nhiệm xác thực JWT bằng public.pem (RS256 verify), kiểm tra Redis blacklist, route request đến đúng service, và rate limiting. Gateway không có private key — chỉ có public key để verify, không thể tạo token giả.

③
Business Service — trung tâm xác thực

Service lõi, giữ cả private key (ký token RS256) và public key (verify nội bộ). Đảm nhiệm tạo token khi login, parse token khi logout/refresh, ghi blacklist vào Redis, và lưu audit log kiểm toán.

④
AI + Publisher Service — nội bộ

Không dùng JWT. Xác thực bằng INTERNAL_SERVICE_KEY (symmetric shared key). JWT dành cho xác thực người dùng bên ngoài. Giao tiếp nội bộ giữa trusted services dùng shared key đơn giản hơn và hiệu quả hơn.

⑤
Luồng dữ liệu

Client → Gateway (JWT) → Gateway verify → inject headers → forward đến Business/AI/Publisher → response trả về qua Gateway đến Client. Gateway đảm bảo chỉ request hợp lệ mới vào được hệ thống nội bộ.

Điểm quan trọng: Phân tách trách nhiệm — Business Service ký token (private key an toàn), Gateway verify (chỉ public key), nội bộ dùng shared key. Mỗi service chỉ làm việc của mình, giảm thiểu rủi ro bảo mật.

5. Giải Thích Chi Tiết Cơ Chế

RS256 = RSA + SHA-256 asymmetric signing. Business Service ký token bằng private key, API Gateway verify bằng public key. Gateway không thể tạo token giả — chỉ verify.

5.0 JWT Là Gì?

JWT (JSON Web Token) là một chuỗi văn bản chứa thông tin định danh người dùng, được ký điện tử để đảm bảo không ai giả mạo. JWT có 3 phần phân cách bằng dấu chấm (.):

header.payload.signature eyJhbGciOiJSUzI1NiJ9. ← header (base64) eyJzdWIiOiIxMjM0Iiwicm9sZSI6In0. ← payload (base64) rVf2kCj... ← signature (RS256)

Header: chứa thuật toán ký. VD: {"alg":"RS256","typ":"JWT"}

Payload: chứa dữ liệu như userId, role, thời gian hết hạn.

Signature: chữ ký số tạo từ private key, dùng public key để xác minh.

5.1 RS256 Khác HS256 Như Thế Nào?

Tính chấtRS256 (BrandHub dùng)HS256
Loại Bất đối xứng (asymmetric) Đối xứng (symmetric)
Key Private + Public — 2 key khác nhau 1 secret duy nhất
Ai ký? Business Service (private key) Bất kỳ ai có secret
Ai verify? Gateway (public key) — không thể ký Bất kỳ ai có secret (cũng có thể ký luôn)
Nếu leak Public key leak = vô hại Secret leak = ai cũng tạo token giả

Ví dụ: Nếu Gateway bị hack với HS256, attacker lấy secret → tạo token giả role=OWNER → toàn bộ hệ thống compromised. Với RS256, attacker chỉ lấy được public key → vẫn không thể tạo token (thiếu private key).

5.1b Benchmark Hiệu Năng — HS256 vs RS256 vs ES256

Tham khảo bài benchmark độc lập từ devops.vn — kiểm tra JWT verification với 3 thuật toán ở các mức tải khác nhau:

Phân tích kết quả benchmark

HS256 nhanh nhất (~30-70x nhanh hơn RS256) — chỉ là HMAC-SHA256, một phép hash đơn giản. Nhưng HS256 dùng chung 1 secret cho cả ký và verify → nếu Gateway bị hack, attacker tạo được token giả ngay lập tức. Không phù hợp với kiến trúc microservices tách biệt Gateway và Business Service.
RS256 chậm hơn rõ rệt nhưng "dễ sống" — ~60-140µs/verify do phải tính toán RSA 2048-bit. Ở 30k RPS, thêm ~1.5-2.8ms p95. Với BrandHub hiện tại (< 1k RPS giai đoạn đầu), chi phí verify JWT (~0.1ms) nhỏ hơn nhiều so với tổng latency của request (database query, business logic, network).
ES256 chậm hơn cả RS256 dù được quảng cáo "hiện đại hơn". Verify ECDSA P-256 đắt hơn RSA verify do phải tính scalar multiplication trên đường cong elliptic. Token nhỏ hơn (64 bytes vs 256 bytes signature) nhưng lợi ích này không đáng kể với server-to-server.
Tại sao ES256 verify chậm hơn RS256 dù key nhỏ hơn?
ECDSA P-256 dùng key 256-bit (nhỏ hơn RSA 2048-bit) nhưng phép toán trên đường cong elliptic (EC point multiplication) nặng hơn phép lũy thừa modulo của RSA:

• RSA verify: public exponent e = 65537 (216+1) → chỉ 17 phép nhân modulo → verify nhanh.
• ECDSA verify: cần 2 phép scalar multiplication trên đường cong elliptic → tổng chi phí cao hơn RSA verify.

→ RSA ký chậm, verify nhanh. ECDSA ký nhanh, verify chậm. Trong JWT, verify xảy ra ở mỗi request (tần suất cao), ký chỉ khi login/refresh (tần suất thấp). → RS256 phù hợp hơn ES256.

5.1c Kết Luận — Tại Sao BrandHub Chọn RS256

1
Bảo mật phân tách (Separation of Concerns)

Business Service giữ private key → ký token. Gateway chỉ có public key → verify, không thể tạo token giả. Với HS256: một service bị hack → mất secret → toàn bộ hệ thống compromised. Với RS256: Gateway bị hack → attacker chỉ lấy được public key → vẫn không tạo được token giả. Đây là ưu điểm quyết định.

2
Hiệu năng chấp nhận được ở quy mô dự kiến

BrandHub giai đoạn đầu < 1k RPS. Mỗi request mất ~0.1ms verify RS256 — không đáng kể so với database query (vài ms đến vài chục ms). Gateway scale ngang khi traffic tăng. Ở 30k RPS, RS256 thêm ~1.5-2.8ms p95 — vẫn chấp nhận được.

3
Key Rotation linh hoạt

Tạo cặp key mới → deploy public key cho Gateway → xong. Không cần restart Business Service. HS256 đòi hỏi cập nhật tất cả service cùng lúc, phức tạp và rủi ro hơn.

4
Tiêu chuẩn ngành & hệ sinh thái

RS256 phổ biến nhất cho JWT trong microservices. Được jjwt, auth0-jwt, nimbus-jose hỗ trợ tốt. Java stdlib (KeyFactory, X509EncodedKeySpec) hỗ trợ RSA tốt. Dễ tích hợp OIDC/IdP sau này.

5
Không chọn ES256

Verify chậm hơn RS256 (ngược với suy nghĩ "key nhỏ hơn = nhanh hơn"). Stress test 50k RPS chạm trần CPU sớm nhất. Token nhỏ hơn (64 bytes signature) không đáng kể với server-to-server. Java hỗ trợ ECDSA không tốt bằng RSA.

Đánh đổi đã chấp nhận: RS256 chậm hơn HS256 ~30-70x — chấp nhận vì bảo mật > hiệu năng thô trong hệ thống xác thực. Signature 256 bytes (so với 32 bytes HS256) tăng vài trăm bytes HTTP header, không đáng kể. CPU cao hơn → giải pháp: scale Gateway ngang.

Khi nào xem xét lại: BrandHub đạt > 30k RPS thường xuyên → thêm caching layer cho JWT verification (cache theo jti ~5 giây). Không khuyến nghị chuyển sang HS256 chỉ vì hiệu năng — đánh đổi bảo mật quá lớn.

5.2 Chi Tiết Quá Trình Tạo Token (Login)

Khi user đăng nhập, Business Service thực hiện các bước:

1
Xác thực thông tin đăng nhập

Kiểm tra email tồn tại trong DB, dùng BCrypt để so sánh password hash. Nếu sai → ném exception 401.

2
Xây dựng Payload cho Access Token 
{
  "sub": "user-uuid",           // User ID
  "role": "OWNER",               // Quyền trong workspace
  "workspaceId": "ws-uuid",     // Workspace hiện tại
  "jti": "unique-id",           // Mã duy nhất của token này
  "iat": 1689000000,            // Thời điểm tạo (epoch)
  "exp": 1689005400             // Hết hạn sau 15 phút
}
3
Tạo chữ ký RS256

Lấy header + payload, nối bằng dấu chấm, băm SHA-256, ký bằng private key (RSA).

signature = RSA_sign(
  privateKey,
  SHA256( base64(header) + "." + base64(payload) )
)

Chữ ký này là duy nhất: nếu payload thay đổi dù 1 ký tự, chữ ký sẽ khác hoàn toàn.

4
Ghép JWT hoàn chỉnh 
JWT = base64(header) + "." + base64(payload) + "." + base64(signature)
5
Gửi về client

Access token trong response body. Refresh token trong cookie httpOnly (không đọc được bằng JavaScript).

// Business Service: JwtUtil.generateAccessToken() Jwts.builder() .subject(userId) // sub .claim("role", role) // role .claim("workspaceId", workspaceId) // workspaceId .id(UUID.randomUUID().toString()) // jti — mỗi lần khác nhau .issuedAt(new Date()) // iat .expiration(new Date(now + 15phút)) // exp .signWith(privateKey, Jwts.SIG.RS256) // KÝ RS256 .compact(); // → JWT string

5.3 Chi Tiết Quá Trình Verify Token (Gateway)

Khi client gửi request với Authorization: Bearer {token}, Gateway thực hiện:

1
Trích xuất token từ Header

Lấy header Authorization. Kiểm tra bắt đầu bằng "Bearer ". Cắt bỏ "Bearer " → lấy JWT string. Nếu không có hoặc sai format → trả 401 ngay.

2
Tách JWT thành 3 phần 
JWT = eyJhbGciOiJSUzI1NiJ9.eyJzdWIiOiIxMjM0In0.rVf2kCj...

Phần 1 (header):   eyJhbGciOiJSUzI1NiJ9
Phần 2 (payload):  eyJzdWIiOiIxMjM0In0
Phần 3 (signature): rVf2kCj74p9P8...
3
Verify chữ ký RS256 
Cách verify:
1. Lấy phần header + payload: "eyJhbGci...NiJ9.eyJzdWIi...In0"
2. Băm SHA-256 → hash
3. Giải mã signature bằng public key → hash_gốc
4. So sánh hash == hash_gốc ?

Nếu BẰNG → chữ ký hợp lệ, token không bị sửa
Nếu KHÁC → token đã bị can thiệp, trả 401

Giải thích tại sao không sửa được token:

Giả sử attacker sửa payload từ userId=123 thành userId=999. Khi đó hash mới tính ra khác hash cũ. Signature trong token được ký bằng private key (chỉ Business Service có). Attacker không có private key → không thể tạo chữ ký mới → verify thất bại.

4
Kiểm tra Redis Blacklist 
String jti = claims.getId();  // lấy mã duy nhất của token
Redis EXISTS jwt:blacklist:{jti}?
  → true  → token đã bị thu hồi (logout) → 401
  → false → token còn hiệu lực → OK
5
Inject headers cho downstream

Sau khi verify thành công, Gateway thêm các headers vào request:

X-User-Id:      claims.sub       → userId
X-User-Role:    claims.role      → quyền
X-Workspace-Id: claims.workspaceId → workspace

Business Service nhận request với các headers này, không cần xác thực lại JWT. Gateway đã làm việc đó rồi.

// API Gateway: JwtUtil.validateAndExtract() Claims claims = Jwts.parser() .verifyWith(publicKey) // verify RS256 bằng public key .build() .parseSignedClaims(token) // nếu signature sai → JwtException .getPayload(); // lấy dữ liệu // Kiểm tra blacklist String jti = claims.getId(); if (redisTemplate.hasKey("jwt:blacklist:" + jti)) { throw new JwtException("Token revoked"); }

5.4 Chi Tiết Quá Trình Logout (Thu Hồi Token)

Khi user logout, client gửi access token (Authorization header) và refresh token (cookie). Business Service:

1
Verify access token nội bộ

Dùng public key (business-service cũng có public.pem) để verify token, lấy claims.

2
Blacklist access token 
jti = claims.getId();
TTL = claims.getExpiration().getTime() - System.currentTimeMillis();
// Nếu token còn 5 phút → TTL = 300000ms
SETEX jwt:blacklist:{jti} 300000 "true"

Redis tự động xóa key sau TTL giây (khi token hết hạn tự nhiên), không cần cron job cleanup.

3
Blacklist refresh token

Nếu client gửi refresh token trong cookie, blacklist tương tự access token.

4
Ghi Audit Log

Lưu lại sự kiện logout với userId, IP, user-agent để phục vụ kiểm toán bảo mật.

// Business Service: blacklistToken() public void blacklistToken(String token) { Claims claims = parseToken(token); // verify RS256 + lấy claims String jti = claims.getId(); // mã duy nhất của token long ttl = claims.getExpiration().getTime() - System.currentTimeMillis(); // thời gian còn lại if (ttl > 0) { redis.opsForValue().set( "jwt:blacklist:" + jti, "true", ttl, TimeUnit.MILLISECONDS // Redis tự cleanup ); } }

5.5 So Sánh Access Token và Refresh Token

Đặc điểmAccess TokenRefresh Token
Thời gian sống 15 phút 30 ngày
Nội dung userId + role + workspaceId + jti userId + jti (không có role)
Cách gửi Header: Authorization: Bearer {token} Cookie httpOnly (JS không đọc được)
Mục đích Xác thực request API Xin cấp access token mới
Nếu bị lộ Dùng được 15 phút → hết hạn Dùng được 30 ngày → cần bảo vệ kỹ hơn

Tại sao refresh token không chứa role? Vì role có thể thay đổi trong 30 ngày (admin thay đổi quyền). Khi refresh, Business Service query role mới nhất từ database, không dùng role cũ.

5.6 Tóm Tắt Luồng Hoạt Động

①
Login → Business Service: xác thực → ký JWT bằng private.pem (RS256) → trả token
②
Request → API Gateway: verify chữ ký bằng public.pem → check Redis blacklist → inject headers → forward
③
Logout → Business Service: lấy jti → SETEX vào Redis với TTL = thời gian còn lại
④
Request sau logout → Gateway: check Redis → blacklisted → 401
⑤
Access token hết hạn → Client gửi refresh token → Business verify → cấp access token mới

6. Key Distribution

🏢 Business Service

Sign + verify token. Giữ cả private và public key qua env var (không dùng file .pem).

JWT_PRIVATE_KEY (sign) JWT_PUBLIC_KEY (verify)

🚪 API Gateway

Verify token + check Redis blacklist. Chỉ giữ public key qua env var, không sign.

JWT_PUBLIC_KEY (verify only)

🧠 AI Service

Không dùng JWT. Xác thực qua INTERNAL_SERVICE_KEY.

📤 Publisher Service

Không dùng JWT. Xác thực qua INTERNAL_SERVICE_KEY.

10. Docker Config

Cập nhật: Không còn volume mount .pem nữa. Key content đi thẳng qua env JWT_PRIVATE_KEY / JWT_PUBLIC_KEY — không có default, thiếu là app crash lúc startup.
# docker-compose.apps.yml — environment # API Gateway JWT_PUBLIC_KEY: ${JWT_PUBLIC_KEY} # Business Service JWT_PRIVATE_KEY: ${JWT_PRIVATE_KEY} JWT_PUBLIC_KEY: ${JWT_PUBLIC_KEY} JWT_ACCESS_EXPIRATION_MS: 900000 JWT_REFRESH_EXPIRATION_MS: 2592000000

Giá trị thật nằm trong brandhub-infrastructure/docker/.env (gitignored) — PEM gộp thành 1 dòng, ví dụ JWT_PRIVATE_KEY=-----BEGIN PRIVATE KEY-----MIIEvgIBADANBgkq...-----END PRIVATE KEY-----.

11. OpenSSL Verification

Dùng lúc generate key mới — key không lưu file lâu dài, chỉ tồn tại trong env (mục 10).

# Kiểm tra key pair có match không openssl pkey -in private.pem -pubout -outform PEM | openssl md5 openssl pkey -in public.pem -pubin -pubout -outform PEM | openssl md5 # Hai MD5 phải giống nhau # Xem modulus (fingerprint) openssl pkey -in private.pem -pubout -text -noout openssl pkey -in public.pem -pubin -text -noout # Đưa vào env sau khi generate (nén 1 dòng, xoá file .pem tạm) PRIV_ONELINE=$(tr -d '\n' < private.pem) PUB_ONELINE=$(tr -d '\n' < public.pem) echo "JWT_PRIVATE_KEY=$PRIV_ONELINE" # dán vào .env echo "JWT_PUBLIC_KEY=$PUB_ONELINE" # dán vào .env rm private.pem public.pem # không giữ file .pem trên disk
