# Spec — Subscription production observability

Scope: implemented agency Basic→Plus checkout, renewal, SePay webhook, invoices, subscription-period credits/lifecycle. No UI, downgrade, personal checkout, AI-spend workflow, refund or automatic financial correction. No Git commit/push or live deployment/migration.

Request correlation: gateway normalizes one X-Request-Id (safe ASCII identifier, max64) before auth/routing, forwards it and returns it on success/errors. Business normalizes/returns same ID and populates scoped MDC. Subscription HTTP logs have event/service/version/requestId/route/status/duration; domain fulfillment logs reflect committed outcomes only. Never log JWT, API key, raw provider payload, bank account or arbitrary query strings. IDs stay out of metric labels.

Alerts: opt-in subscription-critical targets in existing external collector generate structured SERVICE/DATABASE alert after3consecutive non-PASS probes and one recovery event; emit before ingestion, including when Business cannot receive results. Webhook/financial findings persisted in subscription operational issues with stable fingerprint, first/last seen, occurrence, severity, safe details, resolution and requestId. Backend HTTP counters/timers and issue gauges support centralized collection. No external notification transport is configured or sent by this change; production operators collect worker/service structured logs and use admin API.

Reconciliation: scheduled bounded batches plus admin manual trigger, distributed DB lease, repeatable-read local financial snapshot; external SePay reads strictly outside DB transaction/row locks with rate/budget/page limits. Check wallet/grants/ledger on READY+VERIFIED agencies; fulfilled order benefits/period/current credit; webhook REVIEW_REQUIRED/conflicts; due lifecycle stall with grace. FUTURE credit is not due until activation; unpaid expired orders alone are not alerts.

Provider checks use existing read-only SePay client, configured bank account and exact current merchant mapping. Positive matched incoming transfer (amount/time/order code/account already validated by client) with no corresponding recorded payment produces review finding, never grants credit or synthesizes webhook ID. SePayv2 UUID and webhook transaction IDs cannot be assumed interchangeable. Outage/429/incomplete pagination are UNKNOWN, never proof no payment exists or grounds to clear existing findings. Multiple transfers/late/wrong-amount require review. Preserve polling fairness via last-check tracking, max calls/cycle and bounded pages. Missing provider config is visible as degraded coverage, not false financial success.

Admin-only endpoints under /api/v1/admin/billing/operations: issue list with bounded cursor pagination, reconciliation run result. Fresh database admin validation, owner/creator denied. Findings resolve only when successfully checked underlying condition is healthy; unscanned batches/provider failures do not resolve them. Operational writes never mutate billing orders/payment/subscription/credit or immutable ledger/audit. Missing migration or DB failure must not break existing payment handling; operations job logs failures safely.

Done: RED/GREEN protocol and real PostgreSQL regressions, provider fake failures/pagination, collector outage/recovery tests; existing gateway/backend/monitoring suites pass; migration/runbook/config examples; honest limitations. Existing test-only provider hooks remain out of production.
