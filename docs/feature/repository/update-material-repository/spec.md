# FR 3.6.13 — Update Material Repository Specification

- **Feature ID:** FR 3.6.13
- **Feature Name:** Update Material Repository (`update-material-repository`)
- **Date:** 2026-10-24
- **Status:** Specification Ready (`spec.md` — Stage ① of `spec → plan → task → test`)
- **Scope:** `brandhub-api-gateway`, `brandhub-business-service`, `brandhub-infrastructure`, `brandhub-web`
- **Authoritative Business Rules:** `BR01`–`BR25` from `tuan-research/REPOSITORY_SPEC.md`
- **Dependencies:** `FR 3.6.11` (View Material Repository — supplies `version` and `capabilities`), `FR 3.6.12` (Add Material Repository — handles uploading new retouched binaries with `parent_material_id`)

---

## 1. Problem Statement

Currently, `MaterialController` and `MaterialService` in `brandhub-business-service` have **no endpoint** (`PATCH` or `PUT`) to update a material's metadata after upload, and `MediaDetailPanel.tsx` in `brandhub-web` provides no UI controls to rename a material, update its processing classification (`RAW` $\leftrightarrow$ `RETOUCHED`), update its usage purpose (`MATERIAL` $\leftrightarrow$ `BRAND_REFERENCE`), or allow a Workspace Manager to change its sharing audience (`visibility = INTERNAL | CLIENT` and `client_profile_id`).

Without a dedicated, concurrency-safe metadata update contract:
1. Users cannot fix typos or standardize display filenames (`name`) without re-uploading the file.
2. Unsanitized filenames or arbitrary extension changes could introduce path traversal, CRLF/header injection in `Content-Disposition` during download, or spoofed file extensions that contradict the verified `mime_type`.
3. Uploaders who misclassified an asset's processing state (`RAW` vs `RETOUCHED`) or purpose (`MATERIAL` vs `BRAND_REFERENCE`) cannot correct the label, while unauthorized users might attempt to forge the system-only `WATERMARKED` status or overwrite another Creator's `RAW` file metadata instead of uploading a new retouched derivative (`BR04`, `BR08`, `BR10`).
4. Workspace Managers cannot share an `INTERNAL` deliverable with a `CLIENT` profile once ready, nor revoke a `CLIENT` share back to `INTERNAL` (`BR06`, `BR07`, `BR14`).
5. Concurrent edits by two users would silently overwrite each other because `MaterialDocument` currently lacks an optimistic concurrency `version` check.

---

## 2. Solution

Deliver **FR 3.6.13 — Update Material Repository** by adding an atomic, version-checked `PATCH /api/v1/workspaces/{workspaceId}/materials/{materialId}` endpoint in `brandhub-business-service` and integrating inline editing controls into `MediaDetailPanel` in `brandhub-web`:

1. **Safe Display Name Rename (`BR10`, `REPOSITORY_SPEC.md` §9):**
   - Allow permitted actors to update the display `name` (preserving Unicode/Vietnamese characters, stripping `/`, `\`, control chars, CRLF, and path traversal, and enforcing the canonical file extension matching the verified `mime_type`) while keeping `original_name`, `mime_type`, `file_size`, `s3_key`, and `storage_provider` strictly immutable.
2. **Processing Status (`RAW` $\leftrightarrow$ `RETOUCHED`) & Purpose (`MATERIAL` $\leftrightarrow$ `BRAND_REFERENCE`) Updates (`BR08`, `BR09`):**
   - Allow permitted mutators to toggle `type` between `RAW` and `RETOUCHED` (for `IMAGE` and `VIDEO` materials whose current `type` is `RAW` or `RETOUCHED`) and `purpose` between `MATERIAL` and `BRAND_REFERENCE`.
   - Strictly forbid setting or mutating `type = WATERMARKED` via `PATCH` (`WATERMARKED` is exclusively system-generated by `FR 3.6.15`).
   - Enforce `BR04` & `BR10`: when `Creator B` retouches `Creator A`'s `RAW` file, `Creator B` cannot patch `Creator A`'s metadata and must instead upload a new material via `FR 3.6.12` (`type = RETOUCHED`, `parent_material_id = rawId`).
3. **Manager-Only Audience & Client Profile Management (`BR05`–`BR07`, `BR14`):**
   - Restrict post-creation changes of `visibility` (`INTERNAL` $\leftrightarrow$ `CLIENT`) and `client_profile_id` exclusively to active workspace `MANAGER`s (and `SystemRole.ADMIN`).
   - Enforce lineage audience consistency: derivatives cannot have a broader audience than their parent, and revoking/restricting a parent's audience cascades to any active derivatives in the same workspace so revoked files do not remain exposed via child copies.
4. **Optimistic Concurrency (`expectedVersion`), Audit Trail & Quota Independence (`BR20`, `BR21`, `BR23`):**
   - Require `expectedVersion` on every `PATCH` request, executing an atomic MongoDB conditional update (`version == expectedVersion` $\rightarrow$ `version + 1`) and returning `409 MATERIAL_VERSION_CONFLICT` on stale edits.
   - Record metadata and audience changes in PostgreSQL `audit_logs`.
   - Allow metadata updates even when the Agency is over its storage quota or its paid subscription has expired (`BR20`, `BR21`).

## 3. Authoritative Business Rules Applied (`BR01`–`BR25`)

| Rule ID | Business Rule Summary | Application to FR 3.6.13 (Update Material Repository) |
|---|---|---|
| **BR01** | Single-workspace scope | `PATCH` operates strictly within `{ workspace_id: workspaceId }`; cannot move a material across workspaces. |
| **BR02** | `OWNER` permissions | `OWNER` without an active `MANAGER` or `CREATOR` membership in `workspaceId` is rejected with `403`. |
| **BR03** | `MANAGER` permissions | Can update `name`, `type` (`RAW` $\leftrightarrow$ `RETOUCHED`), `purpose` (`MATERIAL` $\leftrightarrow$ `BRAND_REFERENCE`), and `visibility` / `client_profile_id` on **any** active `READY` material in the workspace. |
| **BR04** | `CREATOR` permissions | Can update `name`, `type` (`RAW` $\leftrightarrow$ `RETOUCHED`), and `purpose` **only** on materials where `created_by == actorUserId`. Cannot change `visibility` / `client_profile_id` (`BR07`). Cannot edit metadata of another user's `RAW` file when retouching (`must upload new material per BR10`). |
| **BR05** | `CLIENT` permissions | Can update `name`, `type` (`RAW` $\leftrightarrow$ `RETOUCHED`), and `purpose` **only** when the material is currently visible to their active `client_profile_id` in `workspaceId` (`visibility == CLIENT` and matching `client_profile_id`) **AND** `created_by == actorUserId`. |
| **BR06** | Sharing scope | Canonical field is `visibility` (`INTERNAL` \| `CLIENT`) paired with `client_profile_id`. Setting `visibility = CLIENT` requires a valid active `client_profile_id` belonging to `workspaceId`; setting `visibility = INTERNAL` sets `client_profile_id = null`. |
| **BR07** | Who can change audience? | Only `MANAGER` (and `SystemRole.ADMIN`) can change `visibility` or `client_profile_id` after creation. `CREATOR` and `CLIENT` receive `403 MATERIAL_AUDIENCE_CHANGE_FORBIDDEN` if they attempt to modify audience fields. |
| **BR08** | Processing classification | Permitted mutators may toggle `RAW` $\leftrightarrow$ `RETOUCHED` on `IMAGE`/`VIDEO` assets. `WATERMARKED` is system-only: neither setting `type = WATERMARKED` nor changing an existing `WATERMARKED` item's `type` is allowed via `PATCH`. |
| **BR09** | Brand reference purpose | Permitted mutators may toggle `purpose` (`MATERIAL` $\leftrightarrow$ `BRAND_REFERENCE`) independently of `media_kind` and `type`. |
| **BR10** | No binary overwrite | `PATCH` never modifies binary bytes, `s3_key`, `file_size`, `mime_type`, or `original_name`. |
| **BR14** | Access revocation | When a `MANAGER` changes `visibility` from `CLIENT` to `INTERNAL` (or to a different `client_profile_id`), subsequent list/detail/preview/download requests by the previous Client are blocked immediately (`404`). Existing active derivatives (`parent_material_id`) in the workspace are also restricted so they do not leak access. |
| **BR15** | Soft-deleted materials | Soft-deleted materials (`deleted_at != null`) cannot be patched (`404`/`409`); they must be restored (`FR 3.6.14`) before editing metadata. |
| **BR20–21** | Over-quota & expired subscription | Metadata updates (`name`, `type`, `purpose`, `visibility`, `client_profile_id`) do not increase `usedBytes` and remain **fully allowed** when the Agency exceeds quota or its subscription expires. |
| **BR23** | Storage provider stability | Changing metadata or audience never changes `storage_provider` (`SYSTEM_GDRIVE` / `SYSTEM_S3`) or migrates the object. |

## 5. User Stories

1. **As a Workspace Manager, Creator, or Client**, I want to rename a material I have permission to edit (supporting Vietnamese Unicode characters while preserving its true file extension and original binary), so that files in the repository have clear, standardized names without re-uploading.
2. **As a Manager, Creator, or Client**, I want the system to block or sanitize dangerous characters (`/`, `\`, `..`, control characters, CRLF) and prevent changing a file's extension to a different format (e.g., renaming `.png` to `.pdf` or `.exe`), so that downloads and previews remain safe from path traversal and header injection.
3. **As a Manager, Creator, or Client (on my own uploaded file)**, I want to update a material's processing classification between `RAW` and `RETOUCHED` when its metadata label needs correction, and see the `"Ảnh chưa chỉnh sửa"` warning (`rawWarning`) appear or disappear immediately based on the updated `type`.
4. **As a Manager, Creator, or Client (on my own uploaded file)**, I want to update a material's `purpose` between `MATERIAL` (production asset) and `BRAND_REFERENCE` (Client reference document), so that reference files and production assets are categorized accurately.
5. **As a Workspace Manager**, I want to change any workspace material's audience between `INTERNAL` and `CLIENT` (selecting a specific active `client_profile_id` in the workspace), so that I can share approved deliverables with a Client or revoke a Client's access back to `INTERNAL` (`BR03`, `BR06`, `BR07`, `BR14`).
6. **As a Workspace Creator or Client**, I want the UI and API to prevent me from changing a material's `visibility` or `client_profile_id` after upload (`BR07`), and prevent me from editing the metadata of materials created by other users (`BR04`, `BR05`).
7. **As a Workspace Creator (`Creator B`) viewing a `RAW` photo uploaded by `Creator A`**, I want the detail panel to show `RAW` metadata as read-only for me while providing a clear action to upload my retouched file as a **new** linked material (`FR 3.6.12`), so that `Creator A`'s original `RAW` record is never altered (`BR04`, `BR10`).
8. **As a user attempting to set `type = WATERMARKED` via metadata edit**, I want the system to reject the change because `WATERMARKED` is reserved exclusively for outputs generated by the Watermark Studio (`BR08`).
9. **As a Manager or Creator editing a material while another user modifies the same record**, I want the server to check `expectedVersion` and return `409 Conflict` if my view is stale, so that I do not accidentally overwrite a teammate's rename or audience change.
10. **As a user in an Agency whose storage quota is full or whose paid subscription has expired**, I want to continue renaming materials, updating `RAW` $\leftrightarrow$ `RETOUCHED` / `purpose`, and changing audience scopes without restriction (`BR20`, `BR21`).

## 6. Implementation Decisions

### 6.1 Role & Object-Level Mutation Permission Matrix (`BR02`–`BR09`)

Before evaluating any field change on `PATCH /api/v1/workspaces/{workspaceId}/materials/{materialId}`, the service resolves the caller's active membership in `workspaceId` from PostgreSQL and loads the target `MaterialDocument` scoped by `{ _id: materialId, workspace_id: workspaceId }`:

1. **Existence & Read Visibility Check (404 Before 403):**
   - If the document does not exist in `workspaceId` or has `deleted_at != null`, throw `404 MATERIAL_NOT_FOUND`.
   - If the caller's role in `workspaceId` is `CLIENT` and (`doc.visibility != CLIENT` or `!callerActiveClientProfileIds.contains(doc.clientProfileId)`), throw `404 MATERIAL_NOT_FOUND` (`BR05`, `BR06` — never leak the existence of `INTERNAL` or other clients' files).
2. **State Check:**
   - If `doc.status != READY` (e.g., `UPLOADING`, `VALIDATING`, `REJECTED`, `FAILED`), throw `409 MATERIAL_NOT_READY`.
3. **Field-Level Mutation Authority:**

| Actor in `workspaceId` | Target Material Ownership (`created_by`) | Can Update `name`? | Can Update `type` (`RAW` $\leftrightarrow$ `RETOUCHED`)? | Can Update `purpose` (`MATERIAL` $\leftrightarrow$ `BRAND_REFERENCE`)? | Can Update `visibility` & `clientProfileId`? |
|---|---|---|---|---|---|
| **`MANAGER` (active)** | Any (`created_by` any user) | **Yes** | **Yes** (if `mediaKind in [IMAGE, VIDEO]` and `doc.type != WATERMARKED`) | **Yes** | **Yes** (subject to parent/derivative lineage rules) |
| **`CREATOR` (active)** | Own file (`created_by == user.id`) | **Yes** | **Yes** (if `mediaKind in [IMAGE, VIDEO]` and `doc.type != WATERMARKED`) | **Yes** | **No** (`403 MATERIAL_AUDIENCE_CHANGE_FORBIDDEN` per `BR07`) |
| **`CREATOR` (active)** | Another user's file (`created_by != user.id`) | **No** (`403 MATERIAL_MUTATION_FORBIDDEN`) | **No** (`403` — must upload new material via `FR 3.6.12` per `BR04`, `BR10`) | **No** (`403`) | **No** (`403`) |
| **`CLIENT` (active, matching `client_profile_id`)** | Own file (`created_by == user.id`) | **Yes** | **Yes** (if `mediaKind in [IMAGE, VIDEO]` and `doc.type != WATERMARKED`) | **Yes** | **No** (`403 MATERIAL_AUDIENCE_CHANGE_FORBIDDEN` per `BR07`) |
| **`CLIENT` (active, matching `client_profile_id`)** | Agency staff's file (`created_by != user.id`) | **No** (`403 MATERIAL_MUTATION_FORBIDDEN`) | **No** (`403`) | **No** (`403`) | **No** (`403`) |
| **`OWNER` without `MANAGER`/`CREATOR` membership** | Any | **No** (`403 WORKSPACE_ACCESS_DENIED`) | **No** (`403`) | **No** (`403`) | **No** (`403`) |
| **`SystemRole.ADMIN`** | Any | **Yes** (audited) | **Yes** (audited) | **Yes** (audited) | **Yes** (audited) |

> **Important Edge Case (`BR05` + `BR07`):** If a `CLIENT` originally uploaded a file (`created_by == clientUserId`), and a `MANAGER` later changed that file's `visibility` to `INTERNAL` (revoking Client access), the `CLIENT` no longer satisfies the Read Visibility Check (Step 1) and receives `404 MATERIAL_NOT_FOUND` on any subsequent `GET` or `PATCH`.

### 6.2 Display Name Sanitization & Canonical Extension Rule (`BR10`, `REPOSITORY_SPEC.md` §9)

When `request.name()` is non-null:
1. **Unicode & Control Character Sanitization:**
   - Apply Unicode NFC normalization (`Normalizer.normalize(rawName, Normalizer.Form.NFC)`).
   - Strip all control characters (`\p{Cntrl}`, including `\r`, `\n`, `\t`, `\0`), path separators (`/`, `\`), and quotes (`"`, `'`).
   - Collapse consecutive whitespace into a single space and `.trim()`.
   - Reject if the sanitized name or base name is empty, equals `"."` or `".."`, or contains `".."` (`400 VALIDATION_ERROR`).
2. **Canonical Extension Enforcement:**
   - Determine allowed extensions for `doc.mimeType`:
     - `image/jpeg` $\rightarrow$ `.jpg`, `.jpeg` (canonical `.jpg`)
     - `image/png` $\rightarrow$ `.png`
     - `image/webp` $\rightarrow$ `.webp`
     - `video/mp4` $\rightarrow$ `.mp4`
     - `video/quicktime` $\rightarrow$ `.mov`
     - `application/pdf` $\rightarrow$ `.pdf`
   - If the user provides a base name without an extension (e.g., `"Summer Campaign Hero"` for an `image/png`), automatically append the canonical extension (`"Summer Campaign Hero.png"`).
   - If the user provides an extension that belongs to a **different** format (e.g., renaming an `image/png` to `"contract.pdf"` or `"virus.exe"`), reject with `400 MATERIAL_EXTENSION_MISMATCH` (`"Không được đổi đuôi tệp khác với định dạng thực tế của tư liệu"`).
   - Final `name` length (including extension) must be $1\text{–}255$ characters (`400 VALIDATION_ERROR` if $> 255$).
   - Compute `normalized_name = finalName.toLowerCase(Locale.ROOT)`.

### 6.3 Processing Classification (`type`) & Purpose (`purpose`) Rules (`BR08`, `BR09`)

1. **Updating `type` (`RAW` $\leftrightarrow$ `RETOUCHED`):**
   - If `request.type()` is non-null:
     - If `request.type() == MaterialType.WATERMARKED`, reject with `400 MATERIAL_WATERMARKED_TYPE_IMMUTABLE` (`BR08`: `WATERMARKED` is only assigned by the system).
     - If `doc.type == MaterialType.WATERMARKED` and `request.type() != MaterialType.WATERMARKED`, reject with `400 MATERIAL_WATERMARKED_TYPE_IMMUTABLE` (a watermarked derivative cannot be relabeled as `RAW` or `RETOUCHED`).
     - If `doc.mediaKind == FILE` (`application/pdf`) and `request.type() == MaterialType.RETOUCHED`, reject with `400 INVALID_MATERIAL_TYPE` (`RAW`/`RETOUCHED` applies to media assets; documents stay `RAW`).
2. **Updating `purpose` (`MATERIAL` $\leftrightarrow$ `BRAND_REFERENCE`):**
   - If `request.purpose()` is non-null, update `doc.purpose` to `MATERIAL` or `BRAND_REFERENCE` (`BR09` — independent of `media_kind` and `type`).

### 6.4 Audience (`visibility` & `client_profile_id`) & Lineage Cascade Rules (`BR06`, `BR07`, `BR14`)

When `request.visibility()` or `request.clientProfileId()` is provided:
1. **Role Verification:**
   - Only `MANAGER` (or `SystemRole.ADMIN`) is permitted. If the caller is `CREATOR` or `CLIENT`, throw `403 MATERIAL_AUDIENCE_CHANGE_FORBIDDEN` (even if the submitted values match the existing values, unless omitted/unchanged).
2. **Target State Validation:**
   - If target `visibility == INTERNAL`:
     - Target `client_profile_id` becomes `null` (if `request.clientProfileId()` was non-null while setting `visibility = INTERNAL`, reject with `400 VALIDATION_ERROR`).
   - If target `visibility == CLIENT`:
     - `request.clientProfileId()` (or existing `doc.clientProfileId` if only other fields changed) must be non-null.
     - Verify in PostgreSQL (`workspace_members` joined with `client_profiles`) that `clientProfileId` is an active member with `role = CLIENT` in `workspaceId`. If not, throw `400 CLIENT_NOT_FOUND` / `VALIDATION_ERROR`.
3. **Parent / Derivative Lineage Guard (`REPOSITORY_SPEC.md` §8):**
   - **Case A — Target material is a Derivative (`doc.parentMaterialId != null`):**
     - Load parent material `{ _id: doc.parentMaterialId, workspace_id: workspaceId }`.
     - If parent has `visibility == INTERNAL`, the derivative **cannot** be widened to `visibility == CLIENT` unless the parent is shared first (`409 MATERIAL_DERIVATIVE_AUDIENCE_CONFLICT`).
     - If parent has `visibility == CLIENT` for `profileA`, the derivative can only be `INTERNAL` or `CLIENT` for the **same** `profileA` (`409 MATERIAL_DERIVATIVE_AUDIENCE_CONFLICT` if assigned to `profileB`).
   - **Case B — Target material is a Parent (`parent_material_id == doc.id` exists on active derivatives in `workspaceId`):**
     - If the Manager restricts the parent from `CLIENT (profileA)` to `INTERNAL`, or changes the parent from `CLIENT (profileA)` to `CLIENT (profileB)`:
       - Atomically update all active derivatives in `{ workspace_id: workspaceId, parent_material_id: doc.id, deleted_at: null }` whose audience would otherwise exceed the parent's new audience (e.g., restricting derivatives of `profileA` to match the parent's new `INTERNAL` or `profileB` scope and bumping their `version` + `updated_at`), ensuring no derivative continues leaking access to `profileA` after revocation (`BR14`).

### 6.5 Optimistic Concurrency (`expectedVersion`) & Audit Logging

1. **Atomic Conditional Write:**
   - Execute `MongoTemplate.findAndModify`:
     - **Query:** `{ _id: materialId, workspace_id: workspaceId.toString(), deleted_at: null, status: "READY", version: request.expectedVersion() }`
     - **Update:**
       - `$set`: updated fields (`name`, `normalized_name`, `type`, `purpose`, `visibility`, `client_profile_id`, `updated_by: user.getId().toString()`, `updated_at: Instant.now()`)
       - `$inc`: `{ version: 1L }`
     - **Options:** `FindAndModifyOptions.options().returnNew(true)`
   - If `findAndModify` returns `null` (because another concurrent request incremented `version` or soft-deleted the document in between), re-check existence:
     - If deleted/missing $\rightarrow$ `404 MATERIAL_NOT_FOUND`.
     - If `version != request.expectedVersion()` $\rightarrow$ `409 MATERIAL_VERSION_CONFLICT`.
2. **Audit Trail (`audit_logs` in PostgreSQL):**
   - Persist an `AuditLog` entry with:
     - `agencyId`: resolved from `workspace.agencyId`
     - `userId`: `user.getId()`
     - `action`: `AuditAction.PERMISSION_CHANGE` if `visibility` or `client_profile_id` changed, else `AuditAction.UPDATE`
     - `resourceType`: `"MATERIAL"`
     - `resourceId`: `materialId`
     - `oldValue`: JSON of `{ name, type, purpose, visibility, clientProfileId, version }` before update
     - `newValue`: JSON of `{ name, type, purpose, visibility, clientProfileId, version }` after update

## 7. API Contract

Base path: `/api/v1/workspaces/{workspaceId}/materials`  
Authentication: `Authorization: Bearer <accessToken>`

### 7.1 Update Material Metadata — `PATCH /api/v1/workspaces/{workspaceId}/materials/{materialId}`

- **Allowed Roles:** `MANAGER`, `CREATOR`, `CLIENT` (active member of `workspaceId`, subject to object ACL and ownership rules in §6.1), `SystemRole.ADMIN`.
- **Request Headers:** `Authorization: Bearer <token>`, optional `X-Request-Id`.
- **Request Body (`UpdateMaterialRequest`):**
```json
{
  "expectedVersion": 0,
  "name": "hero-banner-summer-retouched.jpg",
  "type": "RETOUCHED",
  "purpose": "MATERIAL",
  "visibility": "CLIENT",
  "clientProfileId": "770e8400-e29b-41d4-a716-446655440111"
}
```
- **Partial Update Semantics:**
  - `expectedVersion` (`Long`, $\ge 0$) is **always required**.
  - At least one mutable field (`name`, `type`, `purpose`, `visibility`, `clientProfileId`) must be provided (`400 VALIDATION_ERROR` if all optional fields are `null`).
  - Fields omitted (`null`) retain their current stored values, except `clientProfileId` which is automatically set to `null` when `visibility` is changed to `"INTERNAL"`.
- **Success Response (`200 OK`, Header `Cache-Control: no-store`):**
```json

  "success": true,
  "data": {
    "id": "671a0f8b2c4e1a3b5d7f9012",

    "name": "hero-banner-summer-retouched.jpg",
    "originalName": "DSC_0912.jpg",
    "mediaKind": "IMAGE",
    "type": "RETOUCHED",
    "purpose": "MATERIAL",
    "visibility": "CLIENT",
    "clientProfileId": "770e8400-e29b-41d4-a716-446655440111",
    "clientDisplayName": "Nike Vietnam",
    "mimeType": "image/jpeg",
    "fileSize": 4194304,
    "status": "READY",
    "rawWarning": false,
    "previewUrl": "https://storage.example/repository/...?X-Amz-Expires=300&...",
    "previewExpiresAt": "2026-10-24T10:45:00Z",
    "parentMaterialId": null,
```

## 8. Error Handling Contract

| Scenario | HTTP Status | ErrorCode | User-Facing / Client Behavior |
|---|---|---|---|
| Missing or expired JWT | `401 Unauthorized` | `UNAUTHORIZED` / `TOKEN_EXPIRED` | Axios interceptor refreshes token once or redirects to `/login`. |
| Actor is not an active member of `workspaceId`, or is an `OWNER` without `MANAGER`/`CREATOR` membership (`BR02`) | `403 Forbidden` | `WORKSPACE_ACCESS_DENIED` / `FORBIDDEN` | Reject before reading/mutating MongoDB. |
| Material does not exist in `workspaceId`, is soft-deleted (`deleted_at != null`), or is invisible to the calling `CLIENT` (`INTERNAL` or another Client's profile) | `404 Not Found` | `MATERIAL_NOT_FOUND` | Detail panel closes or shows `"Tư liệu không tồn tại hoặc đã bị xóa"`. |
| `CREATOR` or `CLIENT` attempts to edit a material created by another user (`created_by != user.id`) (`BR04`, `BR05`) | `403 Forbidden` | `MATERIAL_MUTATION_FORBIDDEN` | Toast error explaining only the uploader or Workspace Manager can edit this material's metadata. |
| `CREATOR` or `CLIENT` attempts to change `visibility` or `clientProfileId` (`BR07`) | `403 Forbidden` | `MATERIAL_AUDIENCE_CHANGE_FORBIDDEN` | Toast error explaining only a Workspace Manager can change sharing audience. |
| Missing `expectedVersion`, empty update payload, blank/overlong `name` ($>255$ chars), or `visibility = CLIENT` without a valid active `clientProfileId` in `workspaceId` | `400 Bad Request` | `VALIDATION_ERROR` | Inline field error under the offending input. |
| `name` includes an extension that mismatches the material's verified `mime_type` (e.g., `.pdf` on an `image/png`) | `400 Bad Request` | `MATERIAL_EXTENSION_MISMATCH` | Inline error on the name field (`t("repository.extensionMismatchError")`). |
| Attempting to set `type = WATERMARKED` or change the `type` of an existing `WATERMARKED` material (`BR08`) | `400 Bad Request` | `MATERIAL_WATERMARKED_TYPE_IMMUTABLE` | Inline/toast error explaining `WATERMARKED` status is managed by the system. |
| Attempting to set `type = RETOUCHED` on a `FILE` (`application/pdf`) | `400 Bad Request` | `INVALID_MATERIAL_TYPE` | UI hides `RAW`/`RETOUCHED` toggle for `FILE` (`PDF`) items; server rejects with `400`. |
| Material `status` is not `READY` (`UPLOADING`, `VALIDATING`, `REJECTED`, `FAILED`) | `409 Conflict` | `MATERIAL_NOT_READY` | Toast error; editing is disabled until the material is `READY`. |
| `MANAGER` attempts to widen a derivative's audience beyond its parent material (`parent_material_id`) | `409 Conflict` | `MATERIAL_DERIVATIVE_AUDIENCE_CONFLICT` | Inline/toast error explaining a derived file cannot have a broader audience than its parent file. |
| `expectedVersion` does not match the current `version` in MongoDB (concurrent modification) | `409 Conflict` | `MATERIAL_VERSION_CONFLICT` | Preserve user's awareness, show conflict banner (`t("repository.conflict")`) with a `"Tải lại dữ liệu mới nhất"` button to refresh the detail panel. |

## 9. UI/UX, UI States, i18n, Theme & Accessibility (`brandhub-web`)

### 9.1 Metadata Editing UX in `MediaDetailPanel`

In `src/pages/library/components/MediaDetailPanel.tsx` (and extracted sub-component `MaterialMetadataEditForm.tsx` to keep files $< 300$ lines per `rule.md` §13.6):

1. **Capability-Driven Controls:**
   - Read-only view is shown by default, with an `"Chỉnh sửa thông tin"` (`Edit metadata`) `<Button variant="outline" size="sm">` visible whenever `capabilities.canRename || capabilities.canUpdateType || capabilities.canChangeAudience` is `true`.
   - When the user enters Edit mode:
     - **Display Name Input (`name`):**
       - Editable `<Input>` pre-filled with the base name and displaying the locked extension badge (e.g., `.jpg`, `.mp4`, `.pdf`) on `iconSuffix` so users cannot accidentally break the file extension.
       - Enabled only when `capabilities.canRename === true`.
     - **Processing Type Selector (`type`):**
       - Shown for `mediaKind === 'IMAGE' || mediaKind === 'VIDEO'` when `item.type !== 'WATERMARKED'` and `capabilities.canUpdateType === true`.
       - Segmented control / `<Select>` with two options: `Ảnh/Video gốc (RAW)` (`RAW`) and `Đã chỉnh sửa (RETOUCHED)` (`RETOUCHED`). (`WATERMARKED` is never selectable; if `item.type === 'WATERMARKED'`, display a read-only `Đã đóng dấu (Watermarked)` badge).
       - Beneath the selector, display a concise helper note: *"Đổi nhãn phân loại không làm thay đổi nội dung tệp. Nếu bạn vừa chỉnh sửa ảnh/video, hãy dùng nút 'Tải lên bản Retouched mới'."* (`BR08`, `BR10`).
     - **Purpose Selector (`purpose`):**
       - Enabled when `capabilities.canRename` / `capabilities.canUpdateType` is `true`.
       - Options: `Tư liệu sản xuất` (`MATERIAL`) and `Tài liệu tham khảo của Client` (`BRAND_REFERENCE`).
     - **Audience & Client Profile Selector (`visibility` & `clientProfileId`):**
       - Editable **only** when `capabilities.canChangeAudience === true` (`MANAGER` role). For `CREATOR` and `CLIENT`, audience is displayed as a read-only badge (`Nội bộ Workspace` or `Client: {clientDisplayName}`).
       - When `MANAGER` selects `visibility = CLIENT`, render the required Client Profile `<Select>` populated with active workspace clients.
       - If the material has active derivatives or is itself a derivative (`parentMaterialId`), show an informational note about lineage audience rules.
2. **Save, Cancel & Keyboard Interaction:**
   - Pressing `Enter` inside the form submits `PATCH /{id}` with `expectedVersion: item.version`; pressing `Escape` cancels edit mode (or closes the panel if not editing).
   - While saving (`isSaving = true`), `<Button variant="orange" loading>` disables inputs to prevent double submission.
   - On `200 OK`: update the selected material in `MediaDetailPanel`, invalidate TanStack Query cache `['materials', workspaceId]`, exit edit mode, and show `toast.success(t("repository.updateSuccess"))`.
   - On `409 MATERIAL_VERSION_CONFLICT`: display an inline conflict alert inside the form with a `<Button variant="outline">` (`t("repository.reloadLatest")`) that refetches `GET /materials/{id}` and updates the form with the latest `version`.

## Implementation alignment — 2026-10-25
This explicitly supplied spec supersedes the earlier ticket plan. Existing Trash semantics
(DELETED/PURGE_IN_PROGRESS/PURGED, original 30-day restore deadline) are preserved.
PATCH null/omitted values retain stored values as §7.1 specifies; INTERNAL clears profile.
Every valid PATCH increments version, including a supplied unchanged value; stale writes
always conflict. Unknown payload fields are rejected, and binary identity stays immutable.
Audience restriction uses one Mongo replica-set transaction for the target and recursive
lineage, plus the existing ancestor access_revision fence used by uploads/Post/Task pins.
An interrupted transaction rolls back all changes; no partially committed cascade needs a
background saga. Descendants only become more restrictive, never implicitly shared to a
new Client. Existing signed URLs expire within 300 seconds; future issuance rechecks ACL.
Unsafe/unknown legacy storage identities receive no preview fallback or guessed provider.
Usage counters use decimal strings on the wire to preserve PostgreSQL bigint precision.
No live migration, provider reconfiguration, publishing or purge activation is authorized.
