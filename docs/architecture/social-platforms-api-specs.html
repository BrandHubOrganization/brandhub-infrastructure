Facebook Graph API

Version Pinned:
v19.0
Authentication:
Page Access Token (Long-lived)
Endpoint:
POST /{page-id}/feed
Rate Limits:
200 calls/hour per user
Gotchas: Page Access Tokens can suddenly expire if the user changes their password or revokes permissions.
Image Payload Example
// POST /v19.0/{page-id}/photos { "message": "Check out this new image! 📸", "url": "https://brandhub.com/media/sample.jpg", "access_token": "{PAGE_ACCESS_TOKEN}" }

TikTok Content API

Version Pinned:
v2
Authentication:
OAuth 2.0 User Access Token
Endpoint:
POST /v2/post/publish/video/init/
Rate Limits:
1000 calls/day per user
Gotchas: Strict video duration limit: 3s min to 600s max. Multi-step pull-from-url approach is required.
Init Video Publish
// Headers: Authorization: Bearer {TOKEN} { "post_info": { "title": "Amazing TikTok Video #viral", "privacy_level": "PUBLIC_TO_EVERYONE" }, "source_info": { "source": "PULL_FROM_URL", "video_url": "https://brandhub.com/video.mp4" } }

1. Rate Limit Thực Tế Từng Platform (Thứ Dev Phải Handled)

1.1 Meta Facebook Graph API (v19.0)

FB không dùng con số cố định kiểu "x requests/phút". Họ dùng cơ chế CPU Time & Bucket Allocation.

Công thức thực tế: Limit Quota = 200 × Số lượng Active Users trong 24h qua

Thực tế Dev hay gặp:

  • Nếu App mới, ít user (như môi trường Staging/Dev): Chạy vài chục request liên tục là ăn cờ Rate Limit ngay.
  • Header trả về bắt buộc phải đọc: X-App-Usage (Trả về JSON chứa % CPU time, call count).
  • Quy tắc Dev áp dụng: Khi % trong X-App-Usage vượt 80%, hệ thống publisher phải tự Throttle (giảm tốc độ đẩy job). Nếu đạt 100%, FB sẽ block App trong 1 tiếng.

1.2 TikTok Content Posting API (v2)

TikTok là platform gắt gao nhất về Rate Limit vì họ sợ Spam/Bot đăng video hàng loạt.

Giới hạn tầng Request (API Level):

  • creator_info/query: 20 requests / phút / user token.
  • video/init & content/init: 6 requests / phút / user token. (Nghĩa là 1 account TikTok tối đa chỉ được khởi tạo 6 post/phút).

Giới hạn tầng Account/System (Business Level - Cực kỳ quan trọng):

  • Pending Limit: Một user chỉ được phép có tối đa 5 bài đăng ở trạng thái PENDING (đang xử lý/đang upload) trong vòng 24h. Nếu đăng bài thứ 6 khi 5 bài trước chưa xong/chưa được duyệt → Thất bại ngay.
  • Daily Post Cap: Tùy theo độ tin cậy của App/Account (Tier), 1 account thường bị bóp giới hạn đăng 10 - 20 video/ngày qua API.

1.3 Meta Threads API

Threads kế thừa hạ tầng Meta nhưng thiết lập giới hạn cứng (Hard Limit) đơn giản hơn FB Graph API.

  • Giới hạn đăng bài (Publishing Limit): 250 posts / user / 24 giờ (rolling window).
  • Giới hạn Container Creation: Tạo tối đa 1000 containers / user / 24h.

Thực tế Dev xử lý: Giới hạn 250 post/ngày khá thoải mái cho user thường, nhưng với các hệ thống Auto-publisher/Cross-posting:

  • Nếu bắn dồn dập (ví dụ 10-20 bài trong vài giây) → Vẫn dính Spam Detection của Meta dù chưa tới mốc 250 bài/ngày.

1.4 Instagram Graph API (v19.0)

Dùng chung hạ tầng với Meta, nên cơ chế Rate Limit cũng sử dụng thuật toán Token Bucket dựa trên CPU Time.

  • Giới hạn chung: 200 requests / user / giờ đối với tài khoản Professional (Creator/Business).

Thực tế Dev xử lý:

  • Giống với Facebook, hệ thống phải liên tục theo dõi header X-App-Usage và X-Business-Use-Case-Usage.
  • Mặc dù giới hạn giống Facebook, nhưng Instagram API xử lý multi-step (Tạo Container → Publish), nên mỗi bài đăng sẽ tốn ít nhất 2 API calls.

1.5 YouTube Data API (v3)

YouTube không tính theo số lượng request mà tính theo Quota Units.

  • Mỗi Project trên Google Cloud (GCP) mặc định được cấp 10,000 quota units / ngày.
  • Đăng 1 video (tính cả quá trình init) tốn 1,600 units.
  • Nghĩa là tối đa 1 project chỉ đăng được khoảng 6 videos / ngày!

Thực tế Dev xử lý:

  • Khi hết Quota, YouTube API sẽ trả về HTTP 403 với lỗi quotaExceeded.
  • Hạn mức sẽ được reset lại vào lúc 00:00 Pacific Time (PT) hàng ngày.

2. Dev Xử Lý Trong Code & Architecture Như Thế Nào?

Để publisher-service chạy ổn định, không bao giờ gọi trực tiếp API đăng bài từ HTTP Client thông thường mà phải qua Queue & Rate Limiter Pattern.

[API / Client] ──> [Publisher Queue (Redis/RabbitMQ)] │ ▼ [Worker + Rate Limiter Module] │ ├── (Check Token Bucket / Leaky Bucket) ├── (Check Header Usage) ▼ [External Platform APIs (FB/TikTok/Threads)]

Cách 1: Sử dụng Token Bucket Algorithm (Key-Value Redis)

Dev thiết lập Redis key lưu trữ khả năng request còn lại cho từng (Platform + Account ID):

  • TikTok: Set Redis Rate Limiter cho API init post = 5 requests / 60s per user_id.
  • Threads: Counter Redis lưu số post trong ngày (threads:post_count:{user_id}:{date}) ≤ 250.
  • YouTube: Redis lưu tổng quota đã dùng trong ngày cho từng project (youtube:quota_usage:{project_id}:{date}). Trước khi đẩy job qua Queue, nếu cộng thêm 1600 mà > 10000 thì block sớm (Early Reject).

Cách 2: Handle Response Header & Exponential Backoff (Bắt buộc)

Khi dính lỗi Rate Limit, không retry ngay lập tức mà phải retry theo công thức lũy thừa kèm nhiễu ngẫu nhiên (Jitter):

Retry Delay = min(Max Delay, Base Delay × 2attempt + Jitter)

  • Facebook / Instagram: Nếu nhận lỗi code: 4 hoặc code: 17 (User/App level rate limit) → Delay Worker ít nhất 15 - 30 phút. Không retry ngay lập tức.
  • TikTok: Nếu dính HTTP 429 hoặc code: ok_rate_limit → Đọc header Retry-After (nếu có) hoặc hoãn lại 1 - 5 phút.
  • YouTube: Nếu dính HTTP 403 quotaExceeded → Pause Worker/Job đối với project này cho đến 00:00 PT ngày hôm sau (không dùng exponential backoff vài phút vì không có tác dụng).

Cách 3: Media Polling Status Management (Xử lý bất đồng bộ)

Vì TikTok, Threads và Instagram đều bắt buộc khởi tạo Container → Chờ xử lý → Mới Publish:

  • Không dùng while(true) hay Thread.sleep() trong code server để chờ media ready.
  • Đưa vào Status Polling Queue:
  • Sau khi tạo Container, đẩy container_id / publish_id vào một Queue kiểm tra lại sau 30 giây.
  • Thử lại tối đa 5-10 lần. Nếu sau 5 phút media vẫn ở trạng thái IN_PROGRESS / PROCESSING → Đánh dấu Job FAILED để tránh treo tài nguyên worker.
