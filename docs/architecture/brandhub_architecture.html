Auth Role-Check Flow

Vì sao role-check nằm ở business-service, không phải api-gateway

Gateway làm gì

brandhub-api-gateway (Spring Cloud Gateway) chỉ làm 2 việc bảo mật:

  • Verify JWT hợp lệ — JwtAuthFilterGatewayFilterFactory check chữ ký RS256 + check revoke (Redis blacklist). Sai → 401, chặn tại gateway.
  • Rate limiting — giới hạn request theo X-User-Id.

Sau verify, gateway inject 3 header (X-User-Id, X-User-Role, X-Workspace-Id) rồi forward. Gateway không đọc X-User-Role để rẽ nhánh cho phép/từ chối — chỉ nhét header rồi đi tiếp.

Vì sao gateway không check role

  • Chỉ giữ public key (verify chữ ký) — private key chỉ business-service giữ.
  • Không có DB access tới workspace_members — không biết role hiện tại, chỉ biết role lúc JWT issue (claim có thể stale nếu vừa bị đổi role).
  • RBAC theo nghiệp vụ là domain logic của service hiểu nghiệp vụ, không phải trách nhiệm lớp routing/perimeter.

business-service làm gì

JwtAuthenticationFilter tự parse lại JWT từ đầu (đọc thẳng header Authorization, không dùng header gateway đã nhét) — verify độc lập, dựng AuthenticatedUser.

RequireRoleAspect:

  • Check SystemRole (ADMIN bypass hết).
  • Query WorkspaceMemberRepository theo (workspaceId, userId) → lấy MemberRole mới nhất từ DB, không tin claim cũ.
  • So với @RequireRole(...) — không đủ quyền → 403.
Client → api-gateway
  1. verify chữ ký (public key) + check revoke
  2. rate limit
  3. inject X-User-* (chỉ log/debug)
  4. forward nguyên request
→ business-service
  1. JwtAuthenticationFilter tự parse lại JWT
  2. RequireRoleAspect query DB lấy role hiện tại
  3. 403 nếu không đủ quyền
README gateway mô tả "downstream đọc header X-User-*, không re-verify" — thực tế business-service re-verify JWT độc lập, bỏ qua header gateway. Doc cũ chưa cập nhật theo code thật; không ảnh hưởng RBAC middleware.

Local Run Setup

Cách stack local thực sự lắp ráp — khác README gốc (không có docker-compose.yml gộp)

3 file compose tách rời

  • docker-compose.infra.yml — postgres, redis, rabbitmq, chromadb, neo4j. Không mở port host trừ khi có overlay dev.
  • docker-compose.dev.yml — overlay thêm ports: cho infra + service pgadmin.
  • docker-compose.apps.yml — 5 service app, build từ Dockerfile sibling repo (../../brandhub-*).
# scripts/run-compose.bat
docker compose -f infra.yml -f dev.yml up -d          # mặc định
docker compose -f infra.yml -f apps.yml -f dev.yml up -d   # mode "full"

Tách để dev không cần build lại 5 app image — chạy mvn spring-boot:run/npm run dev trực tiếp hot-reload. full dùng khi test nguyên cụm Docker (staging-like).

MongoDB không có trong compose

business-service có biến MONGODB_URI nhưng không service mongo nào trong infra compose — Mongo dùng Atlas cloud, không self-host local. init-mongo.js chạy tay nhắm Atlas, không qua entrypoint init.

Dependency chain (full stack)

postgres/redis/rabbitmq (healthy)
  → business-service (Postgres, Redis, RabbitMQ, Mongo Atlas)
  → api-gateway (chờ business+ai service_started)
  → web-dashboard (chỉ chờ container start, không chờ healthy)
ai-service → chromadb (service_started)
publisher-service → rabbitmq (healthy)

api-gateway là entrypoint duy nhất từ ngoài (8080). Local vẫn mở port 8081/8082/8083 để debug trực tiếp — production không expose.

README hiện tại nói sai: có 1 docker-compose.yml gộp (thực tế 3 file), Mongo container local (thực tế Atlas), version image cũ (postgres:16/rabbitmq:3.13 thay vì 17/3.12).

API mới có tự sync qua Gateway không?

Có — với điều kiện. Cơ chế: wildcard path predicate, không phải service discovery động

Cơ chế thật

brandhub-api-gateway/src/main/resources/application.yml chỉ có 2 route cho business-service:

- id: auth-public
  uri: business-service
  predicates: [Path=/api/v1/auth/**]        # không cần JWT

- id: business-protected
  uri: business-service
  predicates: [Path=/api/v1/**]             # JWT + rate-limit
  filters: [JwtAuthFilter, RateLimit]

Route business-protected match theo path prefix wildcard, không liệt kê từng endpoint. Controller mới trong business-service dùng @RequestMapping("/api/v1/...") → tự động match, tự động đi qua JWT filter + rate limit, không cần sửa gateway config.

Đây không phải service discovery (Eureka/Consul) hay dynamic route registration — chỉ là 1 route Spring Cloud Gateway match theo prefix cố định. "Tự sync" = do path đã nằm trong prefix đã khai báo sẵn, không phải gateway quét code business-service.

Khi nào PHẢI sửa gateway config

  • Endpoint cần public (không JWT) — phải thêm path vào route auth-public hoặc tạo route mới loại trừ JwtAuthFilter. Route business-protected áp JWT cho mọi thứ dưới /api/v1/** trừ khi path đã match route auth-public trước.
  • Thêm service mới (khác business-service) — ai-service, publisher-service hiện chưa có route riêng qua gateway trong application.yml này (chỉ business-service có 2 route). Muốn public qua gateway phải khai báo route + uri mới trỏ service đó.
  • Rate-limit riêng cho nhóm endpoint — cần route/filter config riêng (gateway đã có sẵn biến rate-limit riêng cho AI text/image/video/publish trong docker-compose.apps.yml, nhưng đó là env var đọc bởi filter, không phải route mới).

Tóm lại: thêm API bình thường (có auth, thuộc business-service, dưới /api/v1/) → chỉ code bên service, gateway tự cover. Ngoài phạm vi đó → phải sửa application.yml gateway.
